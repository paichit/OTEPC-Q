# โครงสร้างและประสิทธิภาพ OTEPC Q

ระบบใช้ React + Vite + Tailwind และ Supabase SDK เดิม ไม่เพิ่ม dependency ฝั่งใช้งานจริง

## หน้าที่ของแต่ละส่วน

- `src/App.jsx`: เมนู สถานะร่วม และโหลดหน้าเจ้าหน้าที่/จอแสดงผล/ตั้งค่าเมื่อเปิดใช้
- `src/components/`: หน้าจอและส่วนประกอบ UI; BangkokClock อัปเดตเฉพาะนาฬิกา ไม่ทำให้ทั้งแอป render ทุกวินาที
- `src/hooks/useQueues.js`: ดูแล Realtime หนึ่ง channel, อ่าน snapshot, reconnect และเปลี่ยนวันตามเวลาไทย
- `src/services/refreshQueue.js`: รวมคำขออ่านข้อมูลให้มีหนึ่งคำขอที่กำลังทำงานและหนึ่งชุดรอ อ่านผลตามลำดับ และยกเลิกการอัปเดต state หลัง unmount
- `src/hooks/useAnnouncements.js`: รับทุกเหตุการณ์เรียกคิวเพื่อ TTS การรวมคำขอ snapshot ไม่ตัดเหตุการณ์เสียง
- `src/lib/`: ฟังก์ชันตรวจการตั้งค่า รูปแบบข้อความ และเลือกเสียง ที่ใช้ทดสอบได้โดยไม่เปิดเบราว์เซอร์
- `src/supabaseClient.js`: สร้าง client กลางจาก environment variables
- `supabase/schema.sql`: schema ฉบับเต็มสำหรับฐานข้อมูลใหม่เท่านั้น
- `supabase/migrate-*.sql`: อัปเกรดฐานข้อมูลเดิมตามลำดับใน README
- `tests/`: การทดสอบกติกาคิว สิทธิ์ migration การอ่านข้อมูลพร้อมกัน และ UI
- `scripts/measure-build.mjs`: วัด JavaScript ที่โหลดครั้งแรก รวม static imports และแยกจากไฟล์ lazy-loaded

## สิทธิ์และข้อมูล

| ผู้ใช้ | ทำได้ |
| --- | --- |
| ผู้ใช้ทั่วไป | รับคิวและอ่านรายการของวันนี้ |
| ผู้ที่ไม่มี session เจ้าหน้าที่ | สิทธิ์คิวเหมือนผู้ใช้ทั่วไป |
| เจ้าหน้าที่ที่มี session token ใช้งานได้ | เรียก ถัดไป เรียกซ้ำ ยกเลิกคิวรอ รีเซ็ต และอ่านรายละเอียดประวัติการเรียก |

RLS ไม่อนุญาตให้ผู้ใช้หน้าเว็บเขียนตารางโดยตรง การเปลี่ยนคิวผ่าน RPC ที่ตรวจ session token และใช้ transaction lock เดิม บัญชีเจ้าหน้าที่ไม่ใช้ Supabase Auth หรืออีเมล; PostgreSQL เก็บรหัสผ่านด้วย bcrypt และเก็บเฉพาะแฮชของ token ทุก SECURITY DEFINER ระบุ search_path ว่าง ส่วน queue_snapshot จำกัดวันที่ใน query โดยตรง เพราะทำงานด้วยสิทธิ์เจ้าของฟังก์ชัน ตารางเหตุการณ์ไม่เปิดให้ผู้ใช้ทั่วไปอ่านรายละเอียด

ประวัติการเรียกยังเก็บครบ ไม่ตั้งลบอัตโนมัติเพื่อลดพื้นที่ เพราะจะเสียข้อมูลย้อนหลังที่ผู้ใช้ต้องการ ตารางและคอลัมน์ legacy ยังอยู่เพื่อให้ข้อมูลเดิมใช้ได้

## Migration รอบปรับประสิทธิภาพ

ไฟล์ `supabase/migrate-snapshot-performance.sql` ใช้กับระบบจุดเรียกเดียวที่มี queue_call_events แล้ว หากยังไม่มี ให้ใช้ migrate-recall-cancel.sql ก่อน

- เพิ่ม partial index queues_daily_history เฉพาะสถานะประวัติ ใช้พื้นที่เพิ่มตามจำนวนแถวในประวัติ
- เปลี่ยน queue_snapshot ให้อ่านคิวรอ คิวปัจจุบัน และประวัติล่าสุดแยกกัน เพื่อให้ planner ใช้ดัชนีแต่ละประเภทได้
- ไม่มี DELETE, ไม่มีการเปลี่ยนเลขคิว และไม่ลดสิทธิ์ตรวจสอบเจ้าหน้าที่
- สร้าง index แบบปกติภายใน transaction จึงควรรันช่วงเงียบ เพราะการสร้างอาจพักคำสั่งเขียนชั่วคราว
- รันซ้ำได้: CREATE INDEX IF NOT EXISTS และ CREATE OR REPLACE FUNCTION
- สำหรับฐานข้อมูลเดิม ให้รัน `supabase/migrate-recent-history-50.sql` ต่อจากไฟล์นี้ เพื่อเพิ่มประวัติใน snapshot และหน้าเจ้าหน้าที่จาก 20 เป็น 50 รายการ; รันซ้ำได้และไม่ลบข้อมูล
- ตามด้วย `supabase/migrate-current-and-full-call-history.sql` เพื่อเพิ่ม RPC ประวัติรอบปัจจุบัน (กรองเฉพาะ queue ID ที่ยังอยู่ใน queues วันนี้) และให้ RPC ประวัติเดิมคืนรายการทั้งหมดทุกช่วงเวลา; รันซ้ำได้และไม่แก้/ลบข้อมูลในตาราง
- รัน `supabase/migrate-current-history-cancellations.sql` ต่อท้ายเพื่อให้ประวัติรอบปัจจุบันรวมคิวที่ยกเลิกพร้อมเวลายกเลิก โดยยังไม่จำกัดจำนวนรายการและไม่แก้/ลบข้อมูลเดิม
- ทดสอบ migration เพิ่ม 50 รายการกับ PostgreSQL จำลองแล้ว; ยังไม่ได้ใช้กับ Supabase จริง

## ผลวัด build

หน่วย KB ด้านล่างเท่ากับ 1,000 bytes จากไฟล์ build จริงก่อน/หลัง ไม่ใช่ผลวัดเวลาโหลดเครือข่าย

| รายการ | ก่อน | หลัง |
| --- | ---: | ---: |
| JavaScript ที่โหลดครั้งแรก | 491.47 KB | 468.63 KB |
| JavaScript ครั้งแรกแบบ gzip โดยประมาณ | 140.90 KB | 135.81 KB |
| CSS | 25.26 KB | 22.40 KB |
| CSS gzip โดยประมาณ | 6.55 KB | 5.93 KB |
| ไฟล์ assets รวม | 516.74 KB | 517.29 KB |

ไฟล์รวมเพิ่มประมาณ 0.55 KB จากการแบ่งโหลดและโค้ดจัดการคำขอ/ข้อผิดพลาด แต่หน้าแรกโหลด JS ลดประมาณ 4.6% และ CSS ลดประมาณ 11.4% การปรับหลักด้านการทำงานคือหยุด render ทั้งแอปทุกวินาที และไม่ส่ง snapshot requests ซ้อนกัน ขนาดนี้ไม่รวม Google Fonts ที่โหลดจากภายนอก, HTML และ manifest

`node_modules` มีเครื่องมือพัฒนาและฐานข้อมูลทดสอบ จึงใหญ่กว่าเว็บที่เผยแพร่จริงมาก การ deploy Vercel ใช้ผลใน dist ไม่อัปโหลด node_modules ไปยังผู้ใช้งาน การเพิ่มประวัติใช้งานจริงยังเพิ่มพื้นที่ PostgreSQL ตามปริมาณคิว
